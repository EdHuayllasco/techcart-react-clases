Del tema al contrato

1 · ¿Qué entidad?
UNA sola: recetas, películas, libros, eventos, pokémon, ejercicios. Cinco o seis campos que de verdad vas a mostrar, en español.
2 · ¿De qué API?
Real, gratuita, JSON: DummyJSON (recipes, posts, users, todos), TMDB (películas), PokeAPI, Open Library, países, clima.
3 · ¿Qué colección del usuario?
Favoritos, "por cocinar", lista de lectura, reservas, "ya visto". Es tu carrito: Context + persistencia + su formulario.
// el ejemplo de hoy: recetas de dummyjson.com/recipes
export interface Receta { id: number; nombre: string; imagen: string; cocina: string; dificultad: string; minutos: number; ingredientes: string[]; }
// mapa de rutas: / · /receta/:id · /perfil (protegida) · /login · *

Con el contrato y el mapa de rutas en papel, el resto es el mismo orden de la tienda. La API se traduce en UN archivo: el adaptador.

Integración con un backend propio

No cambia NADA de React
componentes · props · estado · derivados · efectos · rutas · Context · hooks propios · los tres estados de carga · RutaProtegida · memo · lazy
Cero líneas, porque la API está detrás de un adaptador.
Cambian 4 cosas, todas en infraestructura
1 · la URL base → variable de entorno
2 · la forma del JSON → el adaptador (Spring pagina en content)
3 · el campo del token (token, no accessToken) y la ruta de login
4 · los códigos: 401 sin token o vencido · 403 sin permiso
Cambiar de backend = 1 archivo por asunto + 1 línea de import.
// CORS: el navegador bloquea, no el backend. La respuesta llegó; no te la entrega.
blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
// producción: que el backend autorice tu dominio .vercel.app (y sea https)
// desarrollo: proxy de Vite → server: { proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } } }

Pídelo por escrito antes de escribir el adaptador

El contrato que le pides al backend

1 · URL base
en desarrollo y en producción. La de producción, con https: una página HTTPS no puede pedir a HTTP.
2 · Rutas
las que vas a usar, con su método: GET /api/recetas, GET /api/recetas/{id}, POST /api/auth/login…
3 · Ejemplos
una respuesta real de cada ruta, pegada tal cual. Con eso escribes la interfaz cruda sin inventar nombres.
4 · Token
qué ruta lo entrega, qué campos recibe, y cómo se llama el campo que vuelve.
5 · Duración
cuánto vale el token, y en qué unidad viene (segundos o milisegundos).
6 · Errores
qué códigos devuelven (401 · 403 · 404 · 500) y si mandan un mensaje en el cuerpo que puedas mostrarle al usuario.
7 · CORS
si está habilitado para localhost:5173 y para tu dominio de Vercel.

La mitad de los problemas de integración se resuelven con un ejemplo de respuesta pegado en el chat.

Errores frecuentes en proyectos finales

1 · la tienda con otro nombre
se nota en la primera pregunta de la sustentación. Tu contrato, tu API, tu colección
2 · todo en App
componentes de 300 líneas. La rúbrica pide un componente por archivo con una responsabilidad
3 · sin carga ni errores
pantalla en blanco mientras carga y un catch vacío. Es el tema que más pesa: 1.75
4 · token guardado, nunca enviado
ninguna petición con Authorization: Bearer. La rúbrica lo pide explícitamente
5 · un commit gigante la noche anterior
el proceso vale 3 puntos y el historial de commits es la evidencia
6 · 404 al recargar o .env en el repo
falta vercel.json; o una clave publicada. Revisar antes de entregar
