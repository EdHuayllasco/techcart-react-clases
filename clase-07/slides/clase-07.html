Tres cosas que una sesión tiene que hacer

La sesión que sobrevive

1 · GUARDAR
el usuario se guarda en el disco (almacen.ts) y se lee al arrancar comprobando su forma: token de texto, vencimiento numérico. Si no, no hay sesión.
2 · VALIDAR
un token guardado puede ser viejo o estar anulado. Quien decide es el servidor: GET /auth/me con el token en el header Authorization: Bearer.
3 · EXPIRAR
guardamos cuándo vence (expiraEn) y un setTimeout cierra la sesión en ese instante. La limpieza del efecto lo cancela.
useEffect(() => {
  if (!usuario) return;
  // 1. si ya venció → cerrar · 2. obtenerPerfil(token) → si el servidor lo rechaza, cerrar
  // 3. setTimeout(cerrar, expiraEn - Date.now())
  return () => { controlador.abort(); clearTimeout(temporizador); };
}, [usuario]);

Errores frecuentes de sesión II

1 · guardar el token sin validarlo nunca
que esté en el disco no garantiza nada; un token que el servidor ya anuló seguiría "logueado" para siempre → /auth/me al arrancar
2 · confiar solo en expiraEn

el historial queda con una entrada de más y el botón atrás rebota entre el login y la página protegida

una clave privada publicada ya no sirve, hay que cambiarla. .gitignore primero, commit después; .env.example sí se sube

Render no es pintar

Re-renderizar = React ejecuta la función del componente y compara el resultado con el anterior. Pintar = tocar el DOM, solo donde hubo diferencia. Re-renderizar es barato; React ya minimiza lo caro. Entonces, ¿cuándo optimizar? En tres casos concretos:

memo(Componente)
un componente se re-renderiza porque su PADRE cambió, aunque sus props sean las mismas. memo lo salta si cada prop es el mismo valor u objeto. No bloquea los cambios de Context.
useMemo(fn, deps)
un cálculo pesado se repite en cada render con los mismos datos. Recalcula solo si cambió algo del array; el resultado sigue siendo un valor calculado, no estado.
lazy + Suspense
código que el usuario tal vez nunca visite se descarga igual. lazy(() => import(...)) lo parte en un archivo aparte; Suspense muestra algo mientras llega.
Se optimiza lo que se midió. React DevTools → "Highlight updates" muestra qué se re-renderiza. Con 24 productos nada de esto se nota: se aprende aquí para usarlo donde sí hace falta.

Errores frecuentes de optimización

1 · optimizar sin medir
memo en todo "por si acaso" suma comparaciones que cuestan más de lo que ahorran. Primero Highlight updates, después la herramienta
2 · useMemo con dependencias incompletas
usar adentro una variable que no está en el array devuelve resultados viejos. El linter lo marca: hazle caso
3 · lazy sin Suspense
React no sabe qué mostrar mientras descarga el archivo y muestra un error que lo dice claramente
4 · lazy en TODO
partir la tienda en cuarenta archivos hace que cada clic descargue algo. Se parte por rutas que no todos visitan (Checkout, Login), no Home
